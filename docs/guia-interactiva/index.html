1 · Visión general

Centinela decide, para cada transacción financiera, si abrir un caso de fraude —sin que el cliente espere por ello— y explica esa decisión en lenguaje legible.

El problema que resuelve

Un originador (banco, pasarela de pago) enfrenta dos necesidades en tensión:

Respuesta inmediata

No puede dejar al cliente esperando mientras se analiza el fraude. El acuse debe llegar en milisegundos.

Análisis con contexto

Juzgar una transacción exige compararla con el historial de la cuenta — y eso toma tiempo.

Centinela resuelve la tensión desacoplando la ingesta del análisis: la API responde 202 Accepted al instante, y la detección ocurre después, de forma asíncrona y trazada de extremo a extremo.

Las cinco propiedades que definen el sistema

🎯 Detección con contexto

Cuatro reglas evaluadas contra el historial reciente de la cuenta, no en aislamiento.

📝 Explicabilidad determinista

Plantilla, sin modelo de lenguaje. La misma decisión produce el mismo texto y solo afirma lo que el motor registró.

🔑 Cero credenciales

Managed Identity, OIDC federado y Key Vault. Ninguna contraseña en código, repositorio ni imágenes.

🔍 Trazabilidad individual

Dado un transactionId, se reconstruye su recorrido con tiempos por etapa.

Estado del proyecto: tres semanas completadas · 24/25 issues verificadas · pipeline en main · desplegado y probado de extremo a extremo en Azure.

4 · Componentes en detalle

Cómo funciona cada pieza y por qué existe. Despliega cada una para el detalle.

API de ingesta

Punto de entrada. Recibe POST /api/v1/transactions, valida el contrato, persiste el JSON crudo en Blob y publica transaction-event-v1 en Event Grid. Responde 202 antes de que exista veredicto.

  • Rate limiting por origen (token bucket) — evita que una avalancha dispare el motor por cada petición.
  • Idempotencia por transactionId aguas abajo.
Motor de scoring (4 reglas)

Azure Function disparada por Event Grid. Lee el historial de la cuenta desde Cosmos (una sola partición) y evalúa cuatro reglas. Suma puntos; si superan el umbral (configurable en caliente), encola un caso.

ReglaPuntosSe activa cuando…
Geografía imposible40La distancia y el tiempo entre dos transacciones implican una velocidad imposible.
Comercio de riesgo35El comercio o su categoría figuran en la lista de riesgo.
Velocidad / frecuencia30Demasiadas transacciones en una ventana corta frente a la cadencia habitual.
Monto atípico25El monto supera muchas veces el promedio histórico de la cuenta.
Cada regla registra los valores que la activaron (ciudades, multiplicador observado, cadencia). Sin eso, el explicador no podría redactar la decisión — el enunciado asigna esa responsabilidad al motor, no al explicador.
Consumidor de casos + auditoría inmutable

Lee flagged-case-v1 de la Storage Queue y abre el caso en PostgreSQL. Idempotente por transactionId: reprocesar un mensaje no duplica el caso. La bitácora de auditoría es append-only — un trigger rechaza UPDATE y DELETE.

Explicador (asíncrono, resiliente)

Componente independiente que consulta casos con explanation_state = 'PENDING' y les redacta una explicación determinista.

  • No usa modelos de lenguaje. Es una plantilla; la misma decisión produce el mismo texto siempre.
  • Correspondencia estricta: cada frase sale de un valor que el motor registró. Si falta un dato, la frase se empobrece en vez de inventarlo.
  • Resiliente: si se detiene, los casos siguen abriéndose en PENDING; al restablecerlo, recupera el backlog. Detenerlo no bloquea la detección.
Verificación documental (con manejo de fallos)

Extrae nombre, número de identificación y fechas de un documento cargado. El extractor nunca lanza: un documento ilegible, corrupto o de formato inesperado es un desenlace con estado, no una excepción. El caso queda consultable y el analista recibe el resultado.

Límite declarado: el extractor local (PDFBox) no hace OCR; un escaneo sin texto se reporta como ilegible en vez de devolver campos vacíos.

API de consulta

Dos recursos de solo lectura: GET /transactions/{id}/analysis (score, umbral, reglas activadas — existe para toda transacción puntuada) y GET /cases/{transactionId} (el caso, si se marcó). Un 404 en /cases significa "no fue marcada", que es la respuesta correcta para una transacción normal.

5 · Datos y contratos

Cada tipo de dato vive donde mejor le sirve, y los mensajes entre componentes son contratos versionados.

Dónde vive cada dato

Migraciones (Flyway)

  • V1 — esquema inicial de casos.
  • V2 — auditoría inmutable (append-only).
  • V3 — alineación del modelo y trigger anti-mutación.
  • V4 — explicación con su ciclo de vida, datos del documento y account_id.

Los dos contratos que cruzan el pipeline

transaction-event-v1

API → Event Grid → motor. Notifica la ocurrencia; no lleva score. Incluye traceparent.

flagged-case-v1

Motor → cola → consumidor. Resumen de reglas y puntos; el detalle vive en Cosmos. También lleva traceparent.

El contrato es un dato, no código. Se define en JSON Schema, versionado, y una prueba de contrato rompe el build si el record de Java y el esquema divergen. Es el único punto de verdad compartido entre dos imágenes que no comparten classpath.

7 · Seguridad e identidad

El principio: que no haya ningún secreto que robar. Cada credencial se sustituye por una identidad.

sequenceDiagram participant C as Cliente participant E as Entra ID participant API as API participant MI as Managed Identity participant KV as Key Vault participant DB as Cosmos / PostgreSQL C->>E: Solicita token (app role SERVICE) E-->>C: JWT v2 firmado C->>API: POST + Bearer JWT API->>API: Valida firma, issuer, audience Note over API: 401 si el token no es válido API->>MI: Token para Storage / DB MI-->>API: Token de vida corta API->>KV: Lee cadena de conexión (con su identidad) KV-->>API: Secreto API->>DB: Opera con el token — sin clave en código API-->>C: 202 Accepted

Los cuatro pilares

Datos → Managed Identity

La app pide un token efímero a Azure con su identidad. Nunca guarda una clave.

Pipeline → OIDC federado

GitHub emite un token de vida corta atado a este repo y rama. No hay JSON de service principal que rotar.

Secretos → Key Vault

Las pocas cadenas inevitables se resuelven en arranque por Managed Identity.

Red → Private Endpoints

Los datos no son alcanzables desde internet.

App roles (Entra ID) y RBAC del equipo

La aplicación define cuatro roles: SERVICE (originador), ANALYST, ADMINISTRATOR, AUDITOR. Sobre la suscripción, el equipo usa RBAC a nivel de grupo de recursos: un Owner y varios Contributor — nunca sobre la suscripción, para acotar el alcance de cualquier error.

Un secreto filtrado vale hasta que alguien lo rota; un token OIDC filtrado ya caducó. Esa es la diferencia entre "el secreto está bien guardado" y "no hay secreto".

8 · Las 14 decisiones de arquitectura (ADR)

Un ADR registra qué se decidió, por qué, y qué se sacrificó. Aquí las catorce — y, en cada una, el fragmento de código real que la materializa: la decisión no es una nota de diseño, está escrita en un archivo que puedes abrir.

ADR-001 · Clasificación por modelo de nube (cómputo PaaS, red IaaS)

Por qué El cómputo como PaaS elimina administrar VMs y da escala horizontal de fábrica: menor costo operativo y menor superficie de ataque. El único IaaS es la red (VNet) — la única porción que la célula opera directamente, necesaria para aislar los datos.

En el código Ningún script crea una VM ni un clúster: el cómputo se aprovisiona con az containerapp. La ausencia es la prueba.

scripts/provision-container-apps.sh · scripts/deploy-containers.sh 
# El unico IaaS es la red (VNet + Private Endpoints). El computo es PaaS gestionado:
az containerapp env create ...     # NO existe 'az vm create' ni 'az aks create' en el repo
ADR-002 · Red privada: datos no alcanzables desde internet

Por qué Requisito no negociable. Un firewall por IP es frágil; los Private Endpoints dan una IP privada real dentro de la VNet. Revertir esto con el pipeline ya encima sería la decisión más cara del proyecto — por eso se cierra pronto.

En el código El acceso público se deshabilita y el despliegue se aborta si algo lo reabrió — no basta con crearlo cerrado, se verifica cerrado.

scripts/configure-function-host-storage.sh:124 · configure-private-endpoints.sh:210 
public_access="$(az storage account show ... --query publicNetworkAccess -o tsv)"
[ "$public_access" = "Disabled" ] \
  || die "Storage publicNetworkAccess='$public_access'; se esperaba Disabled."
ADR-003 · Mínimo privilegio del rol Servicio

Por qué El rol Servicio corre desatendido: es el objetivo natural de un atacante. Cada permiso de más es superficie de ataque, así que se justifica uno a uno y se acota al recurso, nunca al grupo ni a la suscripción.

En el código A la identidad que baja imágenes se le asigna un solo rol (AcrPull), y el usuario administrador del registro se deja apagado para que no exista una llave maestra alternativa.

scripts/provision-container-registry.sh:49,133,164 
readonly ACR_PULL_ROLE="AcrPull"                 # el minimo para bajar una imagen
az acr create ... --admin-enabled false          # sin usuario admin (llave maestra)
assign_role "$ACR_PULL_ROLE" "$principal_id" "$scope"   # ese rol, y solo ese
ADR-004 · Alta disponibilidad vs. costo

Por qué La decisión original (App Service, Semana 1) era correr una instancia y escalar a dos solo durante la demo, para no gastar el crédito compartido. Al migrar a Container Apps (ADR-009) la redundancia la da el escalado por carga: mínimo 1, hasta 10 réplicas.

En el código Los mínimos y máximos son variables — subir el piso a 2 para HA permanente es cambiar un valor, no rehacer nada.

scripts/deploy-containers.sh:33-34 
readonly API_MIN_REPLICAS="${CENTINELA_API_MIN_REPLICAS:-1}"   # normal: 1 (costo)
readonly API_MAX_REPLICAS="${CENTINELA_API_MAX_REPLICAS:-10}"  # bajo carga: hasta 10
ADR-005 · Sin secretos: Managed Identity desde el día uno

Por qué El enunciado prohíbe cualquier credencial en código o repositorio. Con Managed Identity la app pide un token efímero a Azure con su propia identidad; no hay cadena de conexión que fugar ni rotar. Solo se creó Key Vault cuando Cosmos impuso un secreto real e inevitable — nunca "por si acaso".

En el código El adaptador usa DefaultAzureCredential (sin claves); en despliegue, una variable elige qué identidad toma, no qué secreto.

scripts/deploy-containers.sh:111 · pom.xml:111 (azure-identity) 
# AZURE_CLIENT_ID selecciona QUE identidad usa DefaultAzureCredential —
# no hay ningun secreto ni connection string que pasar a la aplicacion.
ADR-006 · Stack Java 21 + estructura hexagonal

Por qué Los adaptadores de Azure quedan aislados detrás de puertos, de modo que el pipeline y el cambio a contenedores no tocan el dominio. La regla no es verbal: una prueba rompe la construcción si alguien la viola.

En el código Cinco reglas ArchUnit; esta prohíbe que el dominio o la aplicación toquen el SDK de Azure.

src/test/java/com/centinela/architecture/ArchitectureConventionsTest.java:52 
noClasses()
    .that().resideInAnyPackage("..domain..", "..application..")
    .should().dependOnClassesThat().resideInAnyPackage("com.azure..");
ADR-007 · Cosmos: partición por accountId, Session, TTL

Por qué La consulta dominante del motor es "el historial reciente de esta cuenta". Con accountId como shard key ese historial vive en una sola partición y su costo (RU) es estable con el volumen. La clave es inmutable tras la primera escritura: elegir mal obligaría a migrar todo.

En el código El contrato del evento declara accountId como clave de partición del historial — el diseño queda documentado en el propio tipo.

src/main/java/com/centinela/shared/event/TransactionEvent.java:23 
 * @param accountId cuenta duena de la transaccion y clave de particion del historial
ADR-008 · GitHub Actions con OIDC federado

Por qué El repo ya vive en GitHub y, sobre todo, con OIDC no hay credencial que robar: GitHub emite un token de vida corta atado a este repo y rama.

Se sacrifica Los runners viven fuera de la VNet, así que el bootstrap de PostgreSQL no puede correr desde el pipeline; queda manual. Azure DevOps con agente en la VNet sí podría.

En el código El login no recibe contraseña alguna — solo tres identificadores (client/tenant/subscription), inútiles sin un token firmado por GitHub.

.github/workflows/cd.yml:107 
- uses: azure/login@v2
  with:
    client-id:       ${{ secrets.AZURE_CLIENT_ID }}       # identificadores,
    tenant-id:       ${{ secrets.AZURE_TENANT_ID }}       # no secretos:
    subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }} # sin token OIDC no sirven
ADR-009 · Container Apps, no App Service

Por qué Solo Container Apps ofrece a la vez escalado por concurrencia HTTP, scale-to-zero y nivel gratuito generoso. La API de ingesta espera E/S: su CPU apenas se mueve mientras las peticiones se acumulan, así que una regla por CPU llegaría tarde.

Se sacrifica El slot de staging con swap. Fuera del alcance de la semana, así que es una pérdida aceptable.

En el código La regla de escalado de la API es http por concurrencia, no por CPU.

scripts/deploy-containers.sh:191-193 
--scale-rule-name http-concurrency \
--scale-rule-type http \
--scale-rule-http-concurrency "$API_CONCURRENT_REQUESTS" \   # 10 peticiones en vuelo, no %CPU
ADR-010 · Una métrica de escalado por componente

Por qué La API escala por concurrencia HTTP (su cuello es la espera); el motor por concurrencia de invocaciones que le entrega Event Grid; el explicador por trabajo pendiente y escala a cero, porque no recibe peticiones. Una sola métrica para los tres sería más simple y estaría mal en dos.

En el código Los tres perfiles son distintos por defecto — nótese el explicador con piso 0.

scripts/deploy-containers.sh:32-38 
API_CONCURRENT_REQUESTS=10    # API: concurrencia HTTP
SCORING_MIN_REPLICAS=0 / MAX=8   # motor: por invocaciones (Event Grid)
EXPLAINER_MIN_REPLICAS=0 / MAX=3 # explicador: trabajo pendiente, escala a CERO
ADR-011 · ACR Basic (pagar por no tener un secreto)

Por qué ACR no tiene nivel gratuito. Se pagan ~1,20 USD/semana porque permite pull por Managed Identity. La alternativa gratuita (GHCR) obligaría a guardar un Personal Access Token como secreto de la app — justo la credencial de larga duración que el proyecto evita.

En el código Registro Basic, usuario administrador apagado, pull por identidad — se paga por que no exista un secreto.

scripts/provision-container-registry.sh:133,141 
az acr create ... --sku Basic --admin-enabled false   # sin credencial de registro
# el pull lo hace la Managed Identity con rol AcrPull (arriba, ADR-003)
ADR-012 · La traza viaja dentro del mensaje

Por qué El recorrido cruza dos saltos asíncronos (Event Grid y una Storage Queue) entre cuatro procesos. En un salto asíncrono no hay llamada HTTP que el agente pueda instrumentar; sin el contexto dentro del mensaje, la traza se parte en cuatro trazas inconexas.

En el código El contrato normaliza el traceparent en su constructor: uno ausente o corrupto abre una traza nueva en vez de rechazar el mensaje — la telemetría nunca tumba el negocio.

src/main/java/com/centinela/shared/event/TransactionEvent.java:49 
public TransactionEvent {
    // un traceparent ausente/corrupto NO rechaza la transaccion: abre traza nueva
    traceparent = TraceContext.parseOrNewRoot(traceparent).toTraceparent();
}
ADR-013 · Qué se satura primero (PostgreSQL)

Por qué La API y el motor escalan; Cosmos está particionado. PostgreSQL es una sola instancia B1ms y el límite no es la CPU sino las conexiones simultáneas que abre cada réplica nueva del consumidor y del explicador.

En el código Tres mitigaciones concretas: techo de réplicas del explicador, lotes acotados, y un índice parcial para que el sondeo no recorra toda la tabla de casos.

deploy-containers.sh:38 · CaseExplanationConfiguration.java:36 · V4__case_explanation_and_verification.sql:40 
EXPLAINER_MAX_REPLICAS=3                              # techo de conexiones
@Value("${centinela.explainer.batch-size:25}")       # lotes de 25, no toda la tabla

CREATE INDEX idx_fraud_case_pending_explanation
    ON fraud_case (opened_at)
    WHERE explanation_state = 'PENDING';              -- indice PARCIAL
ADR-014 · Qué cambiaríamos al empezar de nuevo

Reflexión Cuatro cosas, por lo que más costaron:

  1. Instrumentar desde la línea uno. No costó añadir logs, sino que los contratos no tenían dónde llevar el contexto de traza. Ampliar dos contratos ya desplegados costó más que el campo desde el inicio.
  2. Diseñar las reglas pensando en cómo se explicarían.
  3. API de consulta desde la Semana 1.
  4. Contenedores desde el principio (paridad local↔nube).

La cicatriz, en el código El campo traceparent que hoy vive en el contrato es exactamente lo que la lección #1 dice que debió existir desde la Semana 2 — se añadió tarde, de forma aditiva.

Lo que no cambiaríamos: la red privada y Managed Identity desde el día uno. Incómodas al principio, evitaron el problema que no se arregla después.

Tropiezos reales que la guía evita: proveedores sin registrar (error que parece de permisos), la subred de contenedores debe ser /23, Cosmos exige índice de occurredAt, los tokens de Entra deben ser v2 (aud = appId pelado), el bootstrap de PostgreSQL abre una ventana temporal de firewall que se cierra sola, y las imágenes fijan file.encoding=UTF-8 (el JRE Alpine arranca en ASCII).

bash stop.sh     # desmonta todo, incluidos volumenes

No hay emulador local de Event Grid; el salto API→motor se simula con scripts/local/simulate-scoring.sh.

bash scripts/shutdown-daily.sh --start  # lo reenciende

10 · Pipeline CI/CD

GitHub Actions con OIDC federado — cero credenciales almacenadas.

ci.yml — en cada PR

  • pruebas: mvn verify en los dos módulos (unitarias + integración).
  • seguridad: barrido de secretos en el árbol y en el historial de Git; verifica que .env no está versionado.
  • análisis-estático: shellcheck sobre los scripts (compuerta a nivel error; warnings informativos).

cd.yml — al integrar a main

Cinco etapas encadenadas con needs, de modo que una prueba fallida detiene todo antes de construir imagen: construir → probar → imágenes → publicar en ACR → desplegar → verificar salud.

Interruptor de despliegue. Las etapas que tocan Azure se activan con la variable AZURE_DEPLOY_ENABLED=true. Sin ella, un merge corre CI y se detiene limpio en lugar de fallar por falta de OIDC. El cableado del despliegue automático está intacto; solo espera su configuración de una vez.

12 · Observabilidad

La instrumentación permite responder cinco preguntas en ejecución, y reconstruir el recorrido de una transacción individual.

Las cinco preguntas de operación

  1. Latencia del scoring: promedio y percentil superior.
  2. Tasa de transacciones procesadas por unidad de tiempo.
  3. Proporción de transacciones marcadas sobre el total.
  4. Punto exacto de fallo de una transacción que no generó caso.
  5. Componente de mayor latencia del pipeline.

Cada etapa emite una línea en formato clave-valor (no prosa), consultable en KQL sin expresiones regulares frágiles:

stage=SCORING transactionId=tx-001 traceId=13a0… durationMs=235 outcome=SUCCESS

Alerta con umbral justificado

Condición: más de 5 transacciones ingeridas sin puntuar en 15 minutos. Es la única condición que significa "un cliente recibió acuse y el fraude no se evaluó" — exige intervención humana, no se resuelve reintentando. Cinco (no uno) porque el reintento de Event Grid cubre fallos aislados.

13 · Mapa de archivos — para qué sirve cada uno

El proyecto son dos repositorios independientes. Aquí está, archivo por archivo, para qué existe cada uno — extraído del propio encabezado de cada archivo, no inventado.

📦 Centinela

El sistema: la API, el motor, el explicador, la infraestructura y toda la automatización de despliegue. Es lo que se monitorea.

🧪 centinela-lab

El banco de pruebas: un cliente externo puro, sin código compartido, que dispara transacciones (una por causal de fraude + un control normal) contra la API pública de Centinela.

Por qué dos repos y no uno. El lab consume Centinela como lo haría un originador real: por HTTP, con su token. No comparte clases ni base de datos — de hecho copia el contrato a propósito (TransactionPayload) para no depender de él. Así, que el lab funcione prueba que la integración externa funciona; si compartieran código, no probaría nada.
