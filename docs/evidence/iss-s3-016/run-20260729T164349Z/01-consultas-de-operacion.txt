# Consultas de operación

Las cinco preguntas que el enunciado exige poder responder **en ejecución**, más la traza
individual. Se ejecutan sobre Application Insights (pestaña *Logs*) o con
`az monitor app-insights query`.

Todas se apoyan en las líneas que emite `StageTelemetry`, con esta forma estable:

```
stage=SCORING transactionId=tx-001 traceId=4bf9… durationMs=142 outcome=SUCCESS
```

El formato es de pares clave-valor y no prosa a propósito: una redacción bonita obligaría a
extraer los campos con expresiones regulares frágiles, y cualquier cambio de texto rompería
todas estas consultas en silencio.

---

## Base común

```kusto
// Extrae los campos de todas las líneas de etapa. El resto de consultas parte de aquí.
let etapas = traces
    | extend
        etapa      = extract(@"stage=([A-Z_]+)", 1, message),
        txId       = extract(@"transactionId=([^\s]+)", 1, message),
        traceId    = extract(@"traceId=([0-9a-f]+)", 1, message),
        duracionMs = toint(extract(@"durationMs=(\d+)", 1, message)),
        desenlace  = extract(@"outcome=([A-Z]+)", 1, message),
        motivo     = extract(@"reason=""([^""]*)""", 1, message)
    | where isnotempty(etapa);
```

---

## 1. Latencia del scoring: promedio y percentil superior

```kusto
traces
| where timestamp > ago(1h)
| where message has "stage=SCORING"
| extend duracionMs = toint(extract(@"durationMs=(\d+)", 1, message))
| summarize
    promedio = round(avg(duracionMs), 1),
    p95      = percentile(duracionMs, 95),
    p99      = percentile(duracionMs, 99),
    muestras = count()
```

El p95 importa más que el promedio: con un promedio de 80 ms y un p95 de 900 ms, la mayoría de
transacciones va bien y una de cada veinte tarda un segundo. El promedio solo esconde eso.

---

## 2. Tasa de transacciones procesadas por unidad de tiempo

```kusto
traces
| where timestamp > ago(1h)
| where message has "stage=SCORING"
| extend txId = extract(@"transactionId=([^\s]+)", 1, message)
| summarize transacciones = dcount(txId) by bin(timestamp, 1m)
| render timechart
```

Se cuenta `dcount` y no `count` porque un reintento de Event Grid produce varias líneas para
la misma transacción; contarlas todas inflaría la tasa justo cuando algo está fallando.

---

## 3. Proporción de transacciones marcadas sobre el total

```kusto
traces
| where timestamp > ago(24h)
| where message has "stage=SCORING" and message has "outcome=SUCCESS"
| extend
    txId    = extract(@"transactionId=([^\s]+)", 1, message),
    marcada = extract(@"flagged=(true|false)", 1, message)
| summarize arg_max(timestamp, marcada) by txId
| summarize
    total    = count(),
    marcadas = countif(marcada == "true")
| extend proporcion = round(100.0 * marcadas / total, 2)
```

`arg_max` por transacción evita contar dos veces una transacción reprocesada.

---

## 4. Punto exacto de fallo de una transacción que no generó caso

```kusto
// Transacciones que entraron y no llegaron al final del recorrido.
let ventana = 1h;
let publicadas = traces
    | where timestamp > ago(ventana)
    | where message has "stage=EVENT_PUBLISH" and message has "outcome=SUCCESS"
    | extend txId = extract(@"transactionId=([^\s]+)", 1, message)
    | distinct txId;
let puntuadas = traces
    | where timestamp > ago(ventana)
    | where message has "stage=SCORING"
    | extend txId = extract(@"transactionId=([^\s]+)", 1, message)
    | distinct txId;
publicadas
| join kind=leftanti puntuadas on txId
| join kind=leftouter (
    traces
    | where timestamp > ago(ventana)
    | extend
        txId      = extract(@"transactionId=([^\s]+)", 1, message),
        etapa     = extract(@"stage=([A-Z_]+)", 1, message),
        desenlace = extract(@"outcome=([A-Z]+)", 1, message),
        motivo    = extract(@"reason=""([^""]*)""", 1, message)
    | where isnotempty(etapa)
    | summarize arg_max(timestamp, etapa, desenlace, motivo) by txId
) on txId
| project txId, ultimaEtapa = etapa, desenlace, motivo, timestamp
| order by timestamp desc
```

La última etapa registrada **es** el punto de fallo: las posteriores sencillamente no llegaron
a ocurrir. Esta misma consulta alimenta la alerta configurada.

## 5. Componente de mayor latencia del pipeline

```kusto
traces
| where timestamp > ago(6h)
| extend
    etapa      = extract(@"stage=([A-Z_]+)", 1, message),
    duracionMs = toint(extract(@"durationMs=(\d+)", 1, message))
| where isnotempty(etapa) and isnotnull(duracionMs)
| summarize
    p50      = percentile(duracionMs, 50),
    p95      = percentile(duracionMs, 95),
    total_ms = sum(duracionMs),
    muestras = count()
  by etapa
| order by p95 desc
```

Se ordena por p95 y se muestra también `total_ms`. Son dos preguntas distintas: la etapa más
lenta **por transacción** y la que más tiempo consume **en agregado**. Una etapa de 5 ms que
ocurre mil veces cuesta más que una de 300 ms que ocurre diez.

## Traza individual de una transacción

Este es el requisito que un panel agregado no satisface.

```kusto
let tx = "REEMPLAZAR-POR-EL-TRANSACTION-ID";
traces
| where timestamp > ago(2h)
| where message has strcat("transactionId=", tx)
| extend
    etapa      = extract(@"stage=([A-Z_]+)", 1, message),
    duracionMs = toint(extract(@"durationMs=(\d+)", 1, message)),
    desenlace  = extract(@"outcome=([A-Z]+)", 1, message),
    traceId    = extract(@"traceId=([0-9a-f]+)", 1, message),
    motivo     = extract(@"reason=""([^""]*)""", 1, message),
    componente = cloud_RoleName
| where isnotempty(etapa)
| project timestamp, componente, etapa, duracionMs, desenlace, motivo, traceId
| order by timestamp asc
```

Equivalente por línea de comandos:

```bash
bash scripts/verify/verify-trace.sh <transactionId>
```

**Qué mirar.** El `traceId` debe ser el mismo en todas las filas. Si cambia entre dos etapas, la
propagación se rompió en ese salto — normalmente porque el `traceparent` no viajó dentro del
mensaje — y a partir de ahí la traza deja de ser una sola.

## Consumo de telemetría

```kusto
// Ingesta por día, para vigilar los 5 GB gratuitos mensuales.
union withsource=tabla *
| where timestamp > ago(7d)
| summarize GB = round(sum(_BilledSize) / 1024 / 1024 / 1024, 3) by bin(timestamp, 1d), tabla
| order by timestamp desc
```

El tope diario está fijado en 1 GB por `provision-observability.sh`. No por la estimación —que
da menos de 1 GB para todo el proyecto— sino porque un bucle de reintentos ruidoso puede
multiplicar el volumen por veinte en una noche, y el tope convierte un susto de facturación en
una pérdida de datos acotada.
